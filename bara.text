BARA HACKATHON - COMPLETE BUILD PLAN
=====================================

PROJECT NAME
------------
BARA

PURPOSE
-------
BARA is a beginner-friendly software architecture and integration
assistant.

It helps beginner developers understand:

- How frontend connects to backend
- How APIs connect components
- How data flows through an application
- Why frontend/backend integration fails
- Where API contracts don't match
- How to fix integration problems

IMPORTANT DEVELOPMENT RULE
---------------------------
Use IBM Bob Shell as the development agent.

The BARA application itself must work independently after development.

Do NOT make Bob Shell a runtime dependency of BARA.

Do NOT use watsonx.ai for the first MVP.

Build deterministic/static analysis first.

PHASE 4 - PROJECT SCANNER
==================================================

Implement a project scanner.

The scanner should:

- Walk through project directories
- Identify relevant source files
- Ignore node_modules
- Ignore .git
- Ignore virtual environments
- Ignore build output
- Identify frontend files
- Identify backend files

.js
.jsx
.ts
.tsx
.py

Do not attempt to support every programming language in the MVP.


==================================================
PHASE 5 - FRONTEND ANALYZER
==================================================

Detect frontend API calls.

Initially support:

fetch()

axios.get()
axios.post()
axios.put()
axios.patch()
axios.delete()

Extract:

- HTTP method
- URL/path
- request body
- query parameters
- response usage
- source file
- line number

Example:

fetch("/api/users")

should produce:

method: GET
path: /api/users


Example:

fetch("/api/users", {
    method: "POST",
    body: ...
})

should produce:

method: POST
path: /api/users


==================================================
PHASE 6 - BACKEND ANALYZER
==================================================

Initially support FastAPI.

Detect:

@app.get()
@app.post()
@app.put()
@app.patch()
@app.delete()

Extract:

- HTTP method
- route path
- request model
- request fields
- response model
- response fields
- source file
- line number

Example:

@app.get("/api/users")

should produce:

method: GET
path: /api/users


==================================================
PHASE 7 - API NORMALIZATION
==================================================

Normalize paths before comparison.

Examples:

/api/users/
/api/users

should be treated as equivalent.

Handle simple path parameters:

/api/users/123

/api/users/{id}

Do not overcomplicate normalization in MVP.


==================================================
PHASE 8 - MISMATCH DETECTION
==================================================

Detect at least these problems:

1. Missing backend endpoint

Frontend calls:

/api/users

Backend does not provide it.


2. HTTP method mismatch

Frontend:

POST /api/users

Backend:

GET /api/users


3. API path mismatch

Frontend:

/api/users

Backend:

/api/user


4. Request field mismatch

Frontend sends:

username

Backend expects:

name


5. Response field mismatch

Frontend expects:

username

Backend returns:

name


6. Query parameter mismatch

Frontend:

/api/users?limit=10

Backend expects a different parameter.


==================================================
PHASE 9 - STRUCTURED ISSUE FORMAT
==================================================

Every detected issue should contain:

issue_type
severity
frontend_location
backend_location
expected
actual
explanation
suggested_fix

Example:

{
  "issue_type": "PATH_MISMATCH",
  "severity": "high",
  "frontend_location": "...",
  "backend_location": "...",
  "expected": "/api/users",
  "actual": "/api/user",
  "explanation": "The frontend requests /api/users but the backend exposes /api/user.",
  "suggested_fix": "Change one side so both use the same endpoint."
}

==================================================
